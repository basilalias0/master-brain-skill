# master-brain — a Claude Code skill for running a Master chat plus Worker chats

Type `/master-brain` and that chat becomes a **Master**: it sizes every request, picks the cheapest way to do each piece, runs worker chats in their own git worktrees, keeps append-only history files so any chat can resume, and reports to you. With several Masters, a **Chief** sits above them. It works in any project. On first run it onboards the project.

It is built to spend few tokens, because every step re-reads the whole chat: boot is one script call (`scripts/boot.cjs`), each cycle's checks are one more (`scripts/cycle.cjs`: rollover, usage, capacity), the laws digest and onboarding files are generated by scripts, Masters message the Chief only when done, blocked or in need, and six helper modules are bundled inside the skill (read only when used).

## Big work runs in parallel (scale mode)

You do not have to ask for workers. Every request is sized when it arrives (`scripts/scale.cjs size`):

| Class | What happens |
|---|---|
| S | the Master does it itself |
| M | one agent, no question to you |
| L | up to 2 background subagents start right away (one line to you); worker chats start on your yes |
| XL | **scale mode**: research, one round of questions, a costed plan, and you pick the worker count |

In scale mode the Master researches the task, splits the work into waves by dependency, and sends you one message: up to 6 questions, each with a default (scope, the finish line, quality bar, deadline, how much of your usage it may spend), the plan built on those defaults, and a table like this (`scripts/scale.cjs plan`). If your answers change the plan, it re-runs it and sends only what changed:

| workers | wall hours | tokens | extra 5h windows | weekly % | bound by |
|---|---|---|---|---|---|
| 1 | 39 | 4.3M | 0 | 9 | workers |
| 3 | 22 | 4.6M | 0 | 9 | dependencies |
| 4 | 22 | 4.7M | 0 | 9 | dependencies |

This is a sample 50-human-day plan: 3 workers finish in about 22 hours, and a 4th only adds tokens. You answer "how many workers?", they start together, and each finished task frees a slot for the next ready one. Nobody waits for tasks one at a time.

**Model and effort per task.** Workers get their model tier and effort from the task's score (`scripts/scale.cjs size` prints both from five 0-2 factors; `MODELS.md`). Masters and the Chief never switch their own, because a switch re-reads the whole chat uncached. After a failure the skill diagnoses first: missed steps get more effort, real difficulty gets a bigger model. A long worker chat is replaced by a fresh worker that continues from its handoff file instead of being switched. Cheap models start only where tests catch their mistakes, and every task is re-sized after the first look. An optional test gate (`scripts/stop-gate.cjs`, a Stop hook offered at onboarding) keeps workers from reporting done while checks fail.

**Pages are checked by script, not by eye.** `scripts/page-check.cjs` waits until a page is fully ready, checks its text, and compares it with an approved baseline image. The model looks only at a small crop of what changed, and only when the compare fails. That's more exact than a model reading a screenshot, and costs no tokens when the page is right. It uses the project's own Playwright, falling back to an installed Chrome or Edge, and never installs anything.

**Long Chief chats roll over.** Every step re-reads the whole chat, so a long chat costs more on every step. When the Chief passes the rollover point (250k tokens by default; `cycle.cjs` says when), `scripts/rollover.cjs` writes a short handoff: every Master, open tasks, open decisions, locks and running servers. Finished work stays in the project's files. After your yes, a fresh Chief starts from that handoff with the rules copied word for word, not summarized, and archives the old chat (or deletes it, if you chose that at onboarding). Masters work the same way: a Master rolls over between tasks, and a bug found later in a finished area goes to a fresh chat for that area's Master (still the same Master and owner), not the old long chat. Or roll over **in the same chat** (with the reboot hook, offered at onboarding; law 12 `rollover: auto` picks whichever method costs fewer tokens at that moment, counting the steps each needs, and a tie goes to the same chat): the chat clears itself, and a session-start hook (`scripts/reboot.cjs`) gives it back its role and the handoff, so it keeps its session id and no Master has to be told a new one. The next message, a Master's report or yours, starts it; nobody types the boot command.

**Dev servers stop after use.** Servers for browser tests start through `scripts/server.cjs start`, which waits for the port so no model turns are spent polling. They stop after the batched test run and at task end (`server.cjs stop --all`), including child processes such as `pnpm` → `vite`. Only servers the skill started are ever stopped, and boot reports any left running. Costs start as defaults marked "uncalibrated" and learn from your finished tasks (`route-log.cjs --size --pct`). More workers never save tokens: each adds its start-up cost, and your 5-hour window often limits speed before the worker count does. Details: `core/SCALE.md`.

## Install

```bash
git clone https://github.com/basilalias0/master-brain-skill.git ~/.claude/skills/master-brain
node ~/.claude/skills/master-brain/scripts/verify.cjs ~/.claude/skills/master-brain
```

On Windows the folder is `%USERPROFILE%\.claude\skills\master-brain`. Update with `/master-brain update` (fast-forward only, asks first). Needs Node 18 or newer and git. No other dependencies, no network use except cloning a skill you approved.

## Modules are bundled

The six helpers (research, lean, developer, analyzer, tester, decide) ship inside this skill as modules, read only when used. `research` (standard and deep) and `developer` update mode run a **community check** (`core/COMMUNITY.md`): they look for alternatives in issue trackers and community Q&A, then vet each one (date and version, official docs, security, licence, proof) before adopting it. Sites that refuse automated access are reported as not reached, never routed around. When a task touches a field that both a form and the server check, the tester compares the two first, and a form looser than the server, or a 500 on blank or missing input, is fixed in the same change with a test rather than left as "out of scope" (A/B on 2026-11-19: 3/3 against 1/6 for 2.4.x and 0/6 with no skill, `plans/ab-2026-11-19.md`). UI and form flows also get `modules/tester/flows.md`: reproduce a blocker before fixing it, replay the steps already passed, and a bounded robustness pass. Only the optional third-party security-audit skill installs on demand, after you say yes, from `registry.json` at a pinned commit.

Per-project state lives in `<project>/master-brain/`, never in this repo. Keep that folder out of the project's git; master-brain treats a tracked one as untrusted.

## Learning from your project

Every finished task is logged in `<project>/master-brain/routing-log.jsonl`, and decisions and mistakes in `<project>/master-brain/ACTION_LOG.md` (searched, never read whole). Past 200 lines, `scripts/decisions.cjs archive` moves the oldest entries that are not under review to `ACTION_LOG-YYYY-MM.md`, verbatim (a dry run unless you add `--write`); it reads both the current `## DL-NNN — signature` headings and the older `## DL-NNN · date · title` ones. `status` nudges a review after 10 logged tasks or 8 new decision entries, and a mistake that comes back a third time after its fix counts as a failed fix. `/master-brain improve` turns the log into proposals (routing, local-rule, generic) with evidence; nothing changes without your yes. Approved project rules go to `<project>/master-brain/overlay/` (capped, one file per module, never able to relax safety or tests). The installed skill is never edited. `/master-brain contribute` writes a sanitized export of rules you mark general; you send it yourself. Only maintainers with write access push this repo; master-brain never does.

## Languages: verified and not

Checked against each language's real test runner (Node, Python, Go, Java via JUnit, Rust, C# via xUnit, Ruby via RSpec, PHP via PHPUnit): test, skip and assertion counts from the guard matched the runner on a fixture that uses the common skip forms. Not checked: `.only`/focus markers in real runs, other frameworks (for example TestNG, NUnit, Minitest, Pest, Kotest) and unusual skip forms; the guard flags those as "possible new skip form" for a human look. The skill says "not run" when a toolchain is missing.

## Tools it uses, and the fallback without them

Laws name tools logically; `templates/CAPABILITIES.md` maps them, and `scripts/caps.cjs diff` checks that map against the tools a host offers. In the Claude desktop app everything is available: the Chief starts worker sessions itself with `start_session` after your yes (it replaced `spawn_task`, checked 2026-11-18). In the plain CLI:

| Capability | Without it |
|---|---|
| spawn a worker | Master drafts a paste-prompt (`core/LEGACY-INBOX.md`) |
| clear a session | you clear it |
| switch model or effort | you switch it; Master tells you which |
| usage | you tell Master the 5-hour percentage |
| scheduled resume | you type `/master-brain resume` |
