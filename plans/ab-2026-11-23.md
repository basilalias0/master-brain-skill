# A/B 2026-11-23: developer UI rules (v2.8.0 against v2.7.1)

## Setup
- **Scope:** one new task, t11, with 3 cells × 3 runs = 9 runs. All runs used the mid tier at default effort.
- **Cells:**
  - **new**: v2.8.0, `modules/developer/MODULE.md`, which points to `ui.md`.
  - **prev**: v2.7.1, the same module without `ui.md`.
  - **control**: no skill.
- **Not run:** the standard suite (t5, t8, t10). Those tasks read only the tester and lean modules, and v2.7.1 and v2.8.0 have byte-identical copies of both. A run would have measured noise.

## t11: "build the account settings page"
**Fixture:** `ab/fixtures/ui`, a plain HTML/JS page with a fixed API:
- 240 countries, paged and searchable, each request taking 300 ms
- settings saves take 1.2 s, and `marketing` always fails
- payments take 1.5 s and are always declined (402)

**Prompt:** asks only for "production quality". No UI rule is named. The README gives only the DOM hooks a grader needs.

**Grader:** `ab/hidden/t11/grade.cjs` runs Playwright in a real Chrome. Pass means all 10 checks pass. The checks were fixed before any run:
- **C1:** the trigger is at least 48 px tall.
- **C2:** each toggle's hit area is at least 48 px.
- **C3:** the picker works by keyboard:
  - Enter opens it, ArrowDown moves, and Enter picks.
  - ArrowDown reopens it.
  - Esc closes it and returns focus.
- **C4:** opened near the bottom edge, the list stays on screen.
- **C5:** search is debounced (1-2 requests while typing "united").
- **C6:** scrolling loads the next page.
- **C7:** the toggle is optimistic (flips within 150 ms).
- **C8:** a failed save rolls back and shows a message.
- **C9:** payment is not optimistic: no early success, one request on a double click, and the decline is shown.
- **C10:** no page errors.

**Grader checked before the runs:** the reference page (`ab/hidden/t11/reference`) scores 10/10 and the empty fixture 1/10. A copy with no debounce and an instant "Paid" fails exactly C5 and C9.

## What it shows
1. **The gain:**
   - **Touch targets:**
     - new: 48 px, with 48 px toggles.
     - prev and control: triggers of 40-44 px and toggles of 22-44 px.
   - **Keyboard:** ArrowDown on the closed picker reopened it in every new run. It failed in 5 of 6 other runs.
   - **Paging:** scroll paging worked in every new run. 3 of 6 other runs used a "Load more" button only.
2. **No difference** on debounce, optimistic toggles, rollback and non-optimistic payment. All 9 runs passed these. The model already does them unprompted, so those rules in `ui.md` cost tokens without changing behaviour here.
3. **Cost:**
   - About 16% more agent tokens than prev (87.2k vs 74.9k) and more tool calls (17 vs 11). Runs also took longer: 125-156 s against about 77 s.
   - RELEASING step 3 says tokens and tool calls must not be higher, so the gate does **not** pass as written. The pass rate went from 0/3 to 3/3. An exception is the owner's call.
4. **Caveat:** the checks and `ui.md` were written by the same author, so C1-C3 test conventions that `ui.md` states. They are WCAG and APG conventions, not inventions, but the control cannot be expected to know 48 px.
5. **Unverified in every run:** none of the 9 runs wrote automated tests, which build mode requires. 1 new run tried the page in a browser.

## Harness notes
- Playwright is not a dependency. Set `PLAYWRIGHT_FROM` to a folder that has it in its `node_modules`.
- The grader uses the installed Chrome (`channel: 'chrome'`, falling back to Edge).
- Ports 4400 and up are used, one per graded folder.
