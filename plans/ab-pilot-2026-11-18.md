# A/B pilot 2026-11-18: task 4 "a big request goes to scale mode"

New skill only (main at a7fef83), 3 runs, one grader (the Master), mid tier. A pilot: no control cell, no old-skill cell,
so it measures behaviour and cost, not a gain. The rubric was written before the runs and is unchanged.

## Fixture and request
An onboarded Express + Postgres shop API (3 jsonb tables, one smoke test, one idle Master, `master-brain/` gitignored).
Request: multi-tenant billing (tenants, Stripe subscriptions, PDF invoices, usage metering, admin dashboard, failed-payment
emails, audit log), with scope, a two-week deadline, production quality and a 30% weekly budget given up front.
The human was unreachable: each run wrote the message it would send to `out/reply.md` and stopped.

## Rubric (pass = all)
(a) runs `scale.cjs size`, class XL · (b) reads the code before planning · (c) writes `plans/<slug>.json` ·
(d) runs `scale.cjs plan` and shows its table · (e) ends asking how many workers, nothing started · (f) does not re-ask
what the request answered.

## Results
| Run | a | b | c | d | e | f | tool calls | agent tokens | fresh tokens | cache read |
|---|---|---|---|---|---|---|---|---|---|---|
| 1 | pass | pass (code + 2 web checks) | fail | fail | partial | pass | 13 | 89k | 186k | 1.26M |
| 2 | pass | pass (code + 5 web checks, notes file) | fail | fail | partial | pass | 14 | 96k | 208k | 1.51M |
| 3 | **fail** (said XL, never ran the script) | pass | fail | fail | partial | pass | 7 | 75k | 155k | 0.58M |

Pass by the rubric: 0/3. Nothing was started and no project file changed in any run (3/3).

## What it shows
1. **All 3 stopped after the interview**, as `core/SCALE.md` §2 orders it (interview, then plan, then the worker count),
   because the finish line, plan prices and admin login were not in the request. The rubric expected the plan in the
   first reply. The skill costs one extra round trip here: each question already had a default, so the plan could have
   been drafted on the defaults and sent with the questions and the worker-count question. Proposal, not applied.
2. **1 run in 3 skipped the sizing script** and stated the class from judgment. Proposal: the reply quotes the script's
   output line, so a skipped run is visible.
3. **Research was good:** runs 1 and 2 found that Stripe removed legacy usage records (billing meters only) and that
   Postgres row-level security leaks across pooled connections unless set per transaction. Run 2 also reported a vendor
   recommendation it did not verify; it should have been tagged `reported`.
4. **Cost:** 75-96k agent tokens per run (earlier A/B medians 64-76k), 155-208k fresh tokens, cache reads the bulk.
   The weekly window read 66% before and after: the 3 runs moved it less than 1 point, so 1M agent tokens costs under
   about 4% of the weekly window on this plan. A full 36-run suite (~3M agent tokens) would cost under about 12%.
